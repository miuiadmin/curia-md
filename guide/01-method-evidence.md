# 01 证据驱动的裁剪

本章回答九个问题里的第 1、2、4 条：四组判据与 9 类的数字怎么从实测里得来、风格三组为什么被删、载荷为什么没有模板与示例与建档脚本。方法可以压成一句话：先立台账，把「哪条判据真的拦到过东西」变成可复算的数字，再拿数字决定保留什么、砍掉什么。本章讲裁剪过程，难免叙述历史；凡历史处均标「历史」，说明它已不是当前状态，与当前状态分开读。

## 一、口径先行：什么算一次拦截

命中台账是本地审计数据 `.agents/.rule-hits.jsonl`（gitignore，不入库）：一条记录对应一次门禁运行，字段只有 `ts` 与 `ids` 两个。一次拦截 = 一个规则 ID 在一次运行的记录里出现一次；命中总数 = 两档全部记录 `ids` 数组的元素之和。记录内同一 ID 不重复、空 `ids` 的记录不落盘——本章写作时按冻结副本复算核实：两档 615 加 709 行均无重复 ID、无空数组。出处：`.agents/notes/implemented/process/2026-10-05-rule-hit-ledger-error-only.md`「Decision」节。

口径不是一开始就对。历史：台账起初把 error 与 warning 合并记账，常驻告警于是灌账——`types/budget-headroom` 一类命中 444 次、74% 至 82% 的门禁运行都携带，预算族命中一度占全部命中的 55%，台账答不了它该回答的问题「哪条规则真的拦到过东西」；「常驻告警必须清零」的误读还驱动了 30 小时内的 10 次预算加码。2026-10-05 收窄为「命中 = 拦截」：`logRuleHits(root, errors, warnings)` 只让 errors 落盘；旧档归档为 `.rule-hits.v1-20261005.jsonl`，新档从零起计。出处：同笔记「Problem」与「Decision」节。

窗口与规模：现行档覆盖 12 天（2026-10-05 至 10-16），615 行记录逐日有拦截（复算：每天最少 10 行）；历史档 709 行，覆盖 2026-10-02 至 10-05；两档合起来是 2026-10-02 至 10-16 的 15 天窗口。出处：`.agents/research/2026-10-17-curia-2-1-slimming-research.md`「方法与来源」与「经验证据」节；行数与逐日覆盖为本章复算。

台账机制随 Curia 2.1 退役，证据被冻结：两档的逐字节副本入库 `.agents/research/2026-10-17-curia-2-1-rule-hits/`，调研报告里配了可复跑的复算配方（截止口径 2026-10-17 零时；现行档副本共 631 行，其中 615 行在截止口径内，截止后追加的 16 行不参与统计）。冻结快照不是活台账：无写入方、重跑只得同一结果。出处：同调研「证据与出处」的注与「复算配方」节。

## 五、载荷：为什么没有模板、示例、建档脚本（历史）

先回答「为什么没有抽取管道」。2.1 之前，载荷 `create-curia/template` 由 `make-template.mjs` 从参考实现仓抽取生成，有三个结构性毛病：其一，抽取是「复制加改名」——采用方继承参考实现引擎的全重与特定栈的运行限制；其二，耦合单向传导——参考实现每次改动都要求整树重抽；其三，漂移双向发生——单件手抄漏演进、整树重抽带入机制漂移。备选试过也否过：手抄单件补丁出过事故（archive-doc 旧版），P1 盘点改回整树重抽；「继续抽取加守卫」防不住方向问题；「保留抽取只优化清洗」改变不了重抽耦合。2026-10-17 管道退役，载荷改为手工维护的一等资产。出处：`.agents/notes/implemented/process/2026-10-17-curia-2-1-payload-manual-maintenance.md`「Problem」「Decision」「Alternatives considered」节。

## 六、把方法带走：可复制的裁剪步骤

第一步，口径先行。记账前写清「什么算一次命中」：只记 error（命中 = 拦截）、一条运行记录一次、记录格式固定为 `ts` 加 `ids`。口径错则后面的账全错——warning 混账的教训就在第一节。**还没有台账的仓从零开始记**——参考实现的口径收窄也走旧档归档、新档从零起计；先跑出一段窗口，再进后面的步骤。窗口口径以参考实现为准：单仓 12 至 15 天、两档台账合计 1,591 次命中；本包没有更短的校准点。

第二步，冻结证据。删机制前把台账逐字节副本入库（或另行冻结），配复算配方与截止时点；守卫源码固化在基线提交里。冻结快照的判据：无写入方、重跑只得同一结果。

第三步，复算两张表并求差。第一张是命中分布：按 ID 计数、降序排列；第二张是登记集：扫守卫源码里错误/报警构造（`errors.push(`、`warnings.push(`、`fail(`、`errors: [`、`warnings: [` 形态，含跨行）上的 `[scope/rule]` 字面量。**两集求差即零命中清单；反方向（命中但不在登记集）也要逐条归因**——已移除或退役机制的历史命中不追、也不据此说扫描口径不全（本仓 4 条：字数预算两条随机制移除，`curia2/` 与 `records/contract` 属 2.1 已退役的 `curia-*` 工具链，见调研「证据与出处」节）；归不进这类来源的，才回头查登记集是否漏了守卫源文件。**读法钉三点**：构造自起始形态起、到其括号闭合止，构造外的字面量不计；计数按不同 ID 去重（同一 ID 出现多次只算一条，不是字面量出现次数）；文件集与基线提交见第二节。**两段命令都不能只靠本包跑通**（登记集那段在调研「复算配方」节；两段都要参考实现仓的冻结台账副本）；手上只有本包的人，按上述口径在自己的守卫源码上自建即可。计数一段的命令如下：

```bash
# 在冻结副本所在仓的仓根执行，只用 Node（≥ 18）；产出 615 行 / 1,591 次 / 55 个 ID
node -e '
```
