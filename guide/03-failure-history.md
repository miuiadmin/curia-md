# 03 失败史与退役面

本章是这套指南的「负向方法」：记录什么试过不行、为什么不行。它回答九条问题里的第 3、5、9 条——被裁掉的六个治理面各是什么、迁移与采用一棵文档树时静默失败的清单与找法、检查器为什么只报不改。**本章的清单与第五章互补，两章都不是完整清单**（第五章末三条形态未进本章，口径差见第五章「迁移的失败形态」节）。按体裁，本章写历史：出现「当时」「一度」的段落都是历史叙述，现行形态一律以 Curia 2.2 规范与各决策笔记为准。下文引用的路径均为 参考实现仓内相对路径；台账与命中类数字已按减重调研的「复算配方」回源复算。

时间线一句话（供下文引用）：Curia 2.0 是一版重治理设计——默认两根、三档保证（基础纳管 / 事实核验 / 受保护交付）、四个治理对象（Registry、Envelope、Assertion、Run），配一整套 `curia-*` 工具链与 7 道门禁（`.agents/plans/2026-10-14-curia-2-0-master-architecture.md`「一页架构」节）。2.1 是收敛——把 2.0 机械整体删除（一批 51,313 行），换成单脚本多组检查（`.agents/notes/implemented/simplification/2026-10-17-curia-2-1-retirement-and-gate-switch.md`「Decision」节）。2.2 删风格三组、去 `--skip`、载荷从 36 件裁到 21 件（`.agents/notes/implemented/simplification/2026-10-19-curia-2-2-check-groups-and-payload-trim.md`「Decision」节）。2026-10-20 的两轮迁移调研修掉最后一族静默失败（见本章第二节）。

## 一、六个退役治理面

Curia 2.2 规范用一句话给出这份名单：「保留持续拦截真实错误的机械子集（头块与生命周期、家与命名、链接），不做从未触发的治理面（断言、Run、受保护交付、注册表、台账、自证矩阵）」（`.agents/README.md`「背景」节）。这句话的判据来自 2026-10-17 的减重调研与收敛笔记，核心实测是：两档拦截台账合计 1,591 次命中、55 个不同规则 ID，而登记集 143 条规则中 92 条零命中；Curia 2.0 命名空间在 15 天窗口里只有 1 次命中，对应的是 14,356 行 `curia-*` 实现（`.agents/research/2026-10-17-curia-2-1-slimming-research.md`「经验证据」节）。台账口径一句话：命中 = 拦截，只有 error 级入账（`.agents/notes/implemented/process/2026-10-05-rule-hit-ledger-error-only.md`「Decision」节）；数字口径补一句：55 与「143 减 92」差的 4 条是不在登记集的历史命中 ID——字数预算两条（规则已随机制移除）、`curia2/` 与 `records/contract` 各一。两档台账本身已随 2.1 删除，逐字节副本作为冻结证据入库于 `.agents/research/2026-10-17-curia-2-1-rule-hits/`，重跑只会得同一结果（减重调研「证据与出处」节注）。

共同判词一句话：重设计先于经验需求。2.0 的设计输入是四份参考项目复核的抽象（设计意图），不是采用方的用量证据；这些治理层机制在真实采用需求出现之前就写成了内核，并配齐规范、实现与自证，2.0 的设计文档总量（19.4 万字符）比它要约束的规范面大一个量级（`.agents/notes/implemented/architecture/2026-10-17-curia-2-1-convergence.md`「Problem」节；`.agents/research/2026-10-17-curia-2-1-slimming-research.md`「重量分布」节）。因此否决「保留为按需可选」这条辩护时只写了一句：可选机制同样要写规范、写实现、写自证、维护兼容、被采用方理解——「重量的本体是「存在」，不是「强制」；等出现真实采用需求再立项，比现在保留一整套可选面便宜」（同笔记「Alternatives considered」节）。

另一条上位约束是 Owner 2026-10-17 的三条硬约束，它们与 2.0 的形态正面冲突：解耦——「不要跟系统耦合起来，丢到其他项目也可以用。它就是一个文档管理方案」；避免过度设计——「不要加一堆规则校验、脚本校验、门禁之类的东西，真没必要啊」；轻量配套——「最多就是有点轻微的配套脚本，去看一下文档规不规范」（同笔记「Problem」节）。

六个面里，断言、Run、受保护交付是 2.0 的治理对象与保证档；注册表、台账、自证矩阵是更早的实现机制。它们的「未触发」记录并不相同：有的零命中，有的命中过但成了噪音，有的体量与收益失衡——下面逐个分开记，不合并成一句「都没用」。

### 断言（Assertion）

它当时解决什么问题：类型正确、链接可达或门禁全绿，都不能单独证明一条声明仍然成立——版本、哈希、端点、数量、工具、权限和候选身份都会漂移；声明「已核实」或被机器消费的事实，需要来源、范围、观察时间、核验方式、限制和冲突状态（`.agents/plans/2026-10-14-curia-2-0-master-architecture.md`「来源、证据与断言」节；`.agents/notes/rejected/architecture/2026-10-14-curia-2-kernel-and-assertions.md`「Problem」节）。

当时长什么样（字段级）：`Assertion = subject + value + scope + source-ref + state + limits + evidence-ref? + verified-by?`，状态至少区分 `confirmed`、`unverified`、`contradicted`、`not-applicable`；未知与冲突不能被文档 current 或更新日期掩盖；`confirmed` 必须回指实际核验方法或结果，`verified-by` 要区分人类、角色或工具身份及实际动作，不只是一个布尔值。它配套 `SourceRef = uri + revision + locator + observed-at`、`EvidenceRef = kind + path + content-digest + observed-at + IdentityBinding?`；机器摘要用 `Digest = algorithm + canonicalization + value` 三元身份，明文禁裸 hash。实现切片包括本地等值核验、按需保存的核验记录与更正历史、外部断言记录（`.agents/notes/implemented/process/2026-10-15-curia-2-local-assertions.md`；`.agents/notes/implemented/process/2026-10-16-curia-2-persistent-assertions.md`）。

为什么从未触发：2.0 命名空间 15 天仅 1 次命中，对应 14,356 行实现；「按声明启用」的「需」没有出现（减重调研「经验证据」节）。唯一的这次命中是 `curia2/git-env-override`，它在基线提交的自证源码里就是一条被期望触发的断言；命中行只记时点与 ID、不记调用方，确切来源未核实——但减重调研与收敛笔记的判读一致：治理层没有产生过真实拦截（同节；收敛笔记「Alternatives considered」节）。

退役判词：随 2.1 整体删除；2.0 内核提案转 rejected，头块写着「2.1 收敛：治理对象与核验方向不采纳」（`.agents/notes/rejected/architecture/2026-10-14-curia-2-kernel-and-assertions.md` 头块；退役笔记「删除面」节）。保留的风险记录是诚实的：被删机制只剩 git 历史可考，若采用方真的需要断言，重建成本高于保留成本；「15 天 1 次命中」的判定窗口很短，且只覆盖一个仓（收敛笔记「Consequences」节）。

### 持久化 Run

它当时解决什么问题：只读 workflow 只输出临时上下文，不能承担长期留痕、并发追加或终态冻结；仅给 JSON 写上 terminal，或者只校验摘要链，仍允许把整条旧链重算后覆盖（`.agents/notes/implemented/process/2026-10-15-curia-2-run-records.md`「Problem」节）。

当时长什么样（字段级）：`Run = run-id + workflow-id + execution-mode + input-snapshot + checks + outputs + unresolved + outcome`；受跟踪执行才增加 failure policy、steps、evidence completeness 与终态。每个已结束的受跟踪命令只能有一个 `terminal=true`；run-id 与 workflow-id 一经持久化不可重用，step 与 finding 只追加，达到终态后冻结；更正、补证据或重跑必须新开 Run 并携带 corrects / retried-from 引用（无环图）。事件有稳定序号、前一事件的完整摘要和真实时点，排他创建的临时文件加不可覆盖的原子链接发布，竞争同一序号最多一方成功；`check-records.mjs` 校验事件合同与摘要链（规则 ID `records/integrity`），记录存储侧的合同拒绝用 `records/contract`（两者同批出现于台账）（`.agents/plans/2026-10-14-curia-2-0-master-architecture.md`「轻量 workflow 与受跟踪 Run」节；run-records 笔记「Decision」节）。

为什么从未触发：存储只在唯一 Registry 的 `instance.recordStore` 显式启用，而本仓根 Registry 从未启用——「参考实现仓 根 Registry 没有启用此能力，参考项目没有被迁移」（run-records 笔记「Consequences」节）。台账里 `records/contract` 与 `records/integrity` 各 1 次命中，同在 2026-10-15 23:32 的一分钟内（同一条记录里是这两条）；相邻一秒的另一条记录里是 `curia2/git-env-override` 与 `tools/cli-failed`——与自证套件调用 CLI 的形态一致；确切调用来源未核实（台账只记时点与 ID），判读同前：没有产生过真实拦截。

退役判词：随 2.1 删除面整体退役——52 支 `curia-*` 脚本 14,356 行、26 支自证 8,610 行、`run-checks` 编排与旧钩子同批删除，git 历史保留（退役笔记「删除面」节）。「普通阅读不留痕、按需记录」的立场被 2.1 收敛继承为不做——现行规范里没有 Run 概念（`.agents/README.md`）。

### 受保护交付

它当时解决什么问题：原项目规则要求发布、审计签署、受保护权威变更，或操作有外部副作用时，交付需要可核验的证据；这是三档保证的最高一档（基础纳管 / 事实核验 / 受保护交付）（`.agents/plans/2026-10-14-curia-2-0-master-architecture.md`「三档保证」节）。

当时长什么样（字段级）：必须具备候选绑定、不可变证据、持久化 Run、审批、并发保护、幂等和派生完成度；对象级用到稳定 `Artifact ID`、五轴身份（逻辑 ID、修订、载荷摘要、来源快照、候选绑定）、candidate binding、`Promotion facet` 与 `Waiver`（同上；`.agents/notes/rejected/architecture/2026-10-14-curia-2-kernel-and-assertions.md`「受保护交付按对象启用」段）。

为什么从未触发：它是六个面里唯一连「部分交付」都没有的面。2.0 实施计划里「实现受保护写入与 Promotion facet」「受保护 owner、verifier 与 approval 的身份认证绑定」等条目始终未勾选，「认证 verifier、备份恢复 authority 与受保护交付」明文列在未完成事项里（`.agents/plans/2026-10-14-curia-2-0-implementation-plan.md`「未完成事项」节）。也就是说，它没触发不是因为需求数据不足，而是它从未走到可被触发的形态，采用需求也没有出现。

退役判词：随 2.1 收敛整体退役，2.0 计划族翻 `superseded`（master architecture 头块；收敛笔记「Related」节）。这里留下的教训与断言同款：设计输入是抽象而非用量证据，机制在需求出现前写成了内核。

### 类型注册表（doc-type registry）

它当时解决什么问题：类型、家、允许状态、头块字段和检查规则需要一份机器可读的单一权威；此前同一份 schema 有两个家（守卫代码里的硬编码常量与注册表），违反「一事实一归属」（`.agents/notes/implemented/process/2026-10-02-gate-toolchain-optimization.md`「Problem」节）。

当时长什么样：`.agents/doc-types.json` 1,378 行，登记 17 类型 / 7 家 / 10 头块字段 / 114 条规则 ID；投影 `doc-types.md` 326 行；生成器 258 行；加上守卫内联枚举，同一份类型事实一度有四个表示（减重调研「重量分布」节；收敛笔记「五处自相矛盾」第 ⑦ 条）。配套一族检查规则：`types/registry-*`、`types/projection-*`。

触发记录：注册表自身的检查规则几乎全零命中——`types/registry-load`、`types/registry-shape`、`types/registry-orphan-template`、`types/registry-template-missing` 等全部零命中，`types/projection-stale` 3 次（台账复算，口径见减重调研「证据与出处」节）。也就是说，注册表作为机制天天在用，但它自己的守卫从未拦到过东西。

退役判词：随 2.1 退役——注册表 JSON、投影与生成器同批删除；类型权威收为规范「9 类文档」表（人读）与脚本内联枚举（机器读）两份，一致性靠人工纪律（`.agents/GLOSSARY.md`「类型注册表」条；退役笔记「删除面」节）。2.1 有一句关键取舍：「只删代码不动规范」没有采用——规范面（注册表 1,378 行、投影、生成器、114 条规则）才是采用方的理解与维护成本；「规则存在但无人执行、也无法自证，是比删除更坏的形态」（收敛笔记「Alternatives considered」节）。

### 命中台账（rule-hit ledger）

它当时解决什么问题：规则没有身份，就无法回答「你最近拦到过什么」——规则集没有修剪依据，只会在历次会话里单调膨胀（`.agents/notes/implemented/process/2026-10-02-gate-toolchain-optimization.md`「Problem」节）。

当时长什么样：全部守卫输出挂 `[scope/rule]` 形态的规则 ID，失败时 append 进 `.agents/.rule-hits.jsonl`（gitignore 的本地台账）；`run-checks --audit` 静态扫守卫源码取规则全集，对照台账列出零命中规则做删除候选（同笔记「Decision」节）。

第一课是口径：台账起初把 error 与 warning 一视同仁，`budget-headroom` 一类常驻告警命中 444 次、74% 至 82% 的门禁运行都携带、预算类命中占全部命中 55%，台账回答不了它本该回答的问题；口径收窄为「命中 = 拦截」（只记 error）才恢复判读——而在此之前，「常驻告警必须清零」的误读驱动了 30 小时内的 10 次预算加码（`.agents/notes/implemented/process/2026-10-05-rule-hit-ledger-error-only.md`「Problem」节；`.agents/notes/implemented/simplification/2026-10-08-word-budget-removal.md`「Problem」节）。

最终命运是个反转：台账作为机制在 2.1 退役——命中数据不再落盘，拦截情况只看检查器输出（`.agents/GLOSSARY.md`「命中台账」条）；但两档台账成了 2.1 与 2.2 全部裁定的证据基础——92 条零命中、`cjk-space` 296 次、`layout/fence-language` 163 次、链接族 144 次这些数字都出自它。两档的逐字节副本作为冻结证据入库，复算配方公开（减重调研「证据与出处」「复算配方」两节）。

判词：台账作为常驻机制退役，作为一次性证据留存。它也顺带纠正了「从未触发」这个粗口径的偏差——台账一直在记录，但它服务的是修剪决策，不产生拦截价值；修剪决策做完，它的机制使命就结束了。这是六个面里唯一一个退役后以「冻结证据」形态被反复引用的。

### 自证矩阵（self-test）

它当时解决什么问题：「守卫真的在跑」的唯一机械信号——门禁可能在全绿中空转：退出码 0、输出正常、实际什么都没查（`.agents/notes/implemented/architecture/2026-10-17-curia-2-1-convergence.md`「Problem」节）。

当时长什么样：逐规则负例夹具矩阵。模板载荷 25 个 `*-self-test.mjs` 占 8,319 行——69 支脚本 22,006 行里的 37.8%；本仓 26 支自证 8,610 行。自证收尾把行使过的守卫集合与 `run-checks` 导出的 `CHECKS` 比对，有缺口就报红：加第七道门禁而不补夹具会当场失败（减重调研「重量分布」节；`.agents/notes/implemented/bug-fix/2026-10-02-gate-silent-bypass-on-symlinked-path.md`「Consequences」节）。

战绩是实打实的两次真事故。其一，符号链接路径下八份脚本的主模块判定全部失效——`import.meta.url` 给的是真路径，`process.argv[1]` 是调用时写下的路径，在符号链接形态下（临时目录、git worktree、被符号链接进来的目录）两者不相等，整个命令行分支被跳过，门禁一条规则都不查却退出 0；其二，归档封印的 append-only 校验因基准路径不同源、异常被吞掉而整段跳过——「改归档笔记再重新封印一次就能把篡改洗白」，而那是「冻结区永久不可改」的唯一机械保证。两处都由自证套件揪出，那批修复把夹具从 109 条加到 135 条、覆盖从 3/6 到 6/6 道守卫（同笔记「Problem」「Consequences」节）。

为什么退役：8,610 行的体量与收益不成比例；只留两条硬断言（空集必红、异常非零），覆盖弱于原夹具矩阵，属明示取舍（退役笔记「Alternatives considered」节）。判词与代价同句写明：「「守卫真的在跑」的信号弱于自证矩阵……静默失效的检查可能在全绿中被长期信任，这正是 1.0 事故的形态；两条硬断言是最低保留信号」（退役笔记「Consequences」节）。第三条硬断言「根锚点缺失必红」由 2.2 补入（2026-10-19 落地提交 `641981a`，`.agents/README.md` 的「诚实条款」与「适用边界」两处；2.1 退役时只有两条）；2026-10-20 的根锚点修复为它加上「（默认调用下）」限定，并把根改由调用目录决定。

### 六个面之后

六个面之外还有两次同判据的先例，判词都是「护栏变流程税就该砍」：字数预算族——两档台账里 550 次命中（占 35%）后被整体移除，机制退场、篇幅改由提示词引导（`.agents/notes/implemented/simplification/2026-10-08-word-budget-removal.md`「Decision」节）；以及重型链维护税的一个实例——「钩子已装但过期」告警是假阳性（检查与安装用了两套基准），给了一条执行了也不消失的建议，缺陷面随重型链删除才消失（`.agents/notes/rejected/bug-fix/2026-10-15-hook-stale-false-positive.md`「Problem」节）。这两条与六个面共用同一条机制冻结判据：机制只在门禁漏了真问题、或流程税高到开始少写文档时才动（参考实现仓根 `AGENTS.md`「本地附加（不随分发）」第 11 条）。

同批退役、但不在六面名单里的还有一批更小的机制，词条都留了判词：三件套（类型对模板对专属检查的 1:1 约束）、投影文档（从权威源生成并逐字节比对新鲜度的派生文档）、按需索引、晋级（`future/` 转存量只读面，该面已于 2026-10-20 整体归档）、封印（哈希记录与 manifest）、脚手架（2.2 删除的建档器与模板目录）（`.agents/GLOSSARY.md` 各条）。要研究 Curia 的完整负向地图，这份词表是最省事的入口。

## 二、静默失败清单与找法

这里说的静默失败，指不报错、不告警，只是检查没发生、东西没接上；它们共同的外观是「全绿」或「完成」——假绿与假成功。清单来自两轮调研与一次修复批：第一轮（九代理 workflow）测「迁移到其他项目的稳定性到底卡在哪」；第二轮把「本地包是既定前提」作为修正框架，把「无损迁移」拆成两版共 70 条可判定事实项、用实测反例逐条攻击；修复批再补上复核时新发现的同族洞（`.agents/research/2026-10-20-curia-migration-stability.md`；`.agents/research/2026-10-20-curia-lossless-migration-definition.md`；`.agents/notes/implemented/bug-fix/2026-10-20-curia-lossless-migration-fixes.md`）。

先给结论定位：实测到的失败没有一条出在「包怎么送过去」——空宿主上不做任何包化就已经无损（21 件载荷加 3 条桥全落地、退出码 0）；咬人的是宿主路径占用与退出码语义（`.agents/notes/implemented/process/2026-10-20-curia-migration-stability-decisions.md`「Problem」节）。可归因的真实损害在 15 天项目史上约 1 人日（某采用仓为排障花了一天），而三条候选修复路线（包化传输、载荷清单自证、宿主适配协议）合计要新增一个发布仪式与数百行代码——成本与损害不相称，故只修实测出来的假绿，不造新机制（迁移稳定性调研「合成结论」节；修复笔记「Alternatives considered」节）。

清单按根因归成五类形态（**与第五章互补，两章均非完整清单**）。同一条根因会生多个个案；下面每类先给判据式的一句话，再列实测个案。清单覆盖第一轮调研的「五处已实测」、第二轮的「六条反例」，加修复批复核时新发现的复制步落点洞与其同族小项——这是成文记录的并集。

**根因一：判据只看形态，不看解析后的落点——代理指标被穿透。** 个案一：宿主根上 `.claude`/`.codex` 本身是指向仓外的符号链接时（共享 dotfiles 配置的常见形态），安装器把桥建到仓外——`readlink` 逐字正确、退出码 0、重跑报「已就位 3」、检查全绿，而桥是死的、且根本不在仓里；根因是桥步用「`readlink` 字符串相等」加「建链接没抛错」当健康判据，没有做真解析（两名复验员各自独立测出）。个案二：同一形态下的「修复命令」是假成功——打印的 `mv … && ln -s …` 能成功执行：成功地把桥建死、把仓外内容顶走，所有可核判据都显示成功；不是失败，是假成功。个案三：载荷复制步与桥步是同一个洞——宿主把 `.agents/` 预先做成指向仓外的符号链接时，安装器报「完成」、退出码 0、桥 3 条全接上，而整份载荷落在仓外、git 完全看不见；初判曾把它写成「已知边界、不修」，复核时被实测推翻——两者判据都只看形态、不看解析后的落点，「留一半等于留一整个洞」。个案四：已存在的悬空链接（`readlink` 字符串对但目标不存在）曾被算作「已就位」（无损调研「反例」节；修复笔记「Problem」「Decision」节）。修法：判据从「形态」改成「性质」——真解析得到、且落在目标仓内；落在仓外一律拦下、仓外零写入（修复笔记「Decision」节）。

**根因二：锚点或身份取自错误来源。** 个案：检查器的根锚点曾自脚本位置上溯——把脚本放到用户主目录下执行，根锚点会静默锚到主目录里已存在的 `.agents`（全局技能目录），扫 242 篇、退出码 0、零注记；而规范当时写着「脚本位置不限（可搬出 `.agents/tools/`）」，这句只在同树内搬动时成立。同族毛病是那个查找函数的 `catch` 吞掉的不只「不存在」，权限与符号链接错误一样被吞。修法：根锚点改调用目录，默认调用下缺失即退出码 2，不做上溯（迁移稳定性裁定笔记「Decision」节）。

**根因三：退出码与计数把不同事态压成同一个 0。** 个案一：全占用宿主上安装器打印「完成」、退出码 0，而桥 0/3、载荷的 8 条通用规则全树 grep 零命中、检查也全绿（默认面是 `.agents/` 与 `docs/`，根规则文件不在面内）——汇总行的「桥 N 条」是本次新建数，健康重跑与彻底失败同样打印 0，「装了」与「接上了」共用退出码 0。个案二：报告模式有发现也退出码 0——这属有意设计（规范明文），但它是「把检查器直接写进 CI 而漏 `--strict` 就全绿空转」的陷阱。个案三：结构组跳过只给一行 stdout 注记，`--strict` 也 0——注记淹没在报告流里。个案四：冲突清单超过 8 件只列 8 个名加「等」，而承诺是「不是静默」——实测 10 件冲突有 2 件不具名（迁移稳定性调研「实测证据」节；修复笔记「Decision」节）。修法：桥步改三分计数（新建 / 已就位 / 未接上）并新增退出码 3；结构组注记移 stderr、汇总行自带标注（退出码不动——规范明文承认部分改名仍可能以 0 加注记告终，有注记、非失败）；每次调用打印「被检树」身份行；冲突清单一行一件全列（迁移稳定性裁定笔记「Decision」节；修复笔记「Decision」节）。

**根因四：声明面之外的输入静默不进面——「全绿」可以是空承诺。** 个案一：扫描面只收 `.md`，`.mdx`/`.markdown` 不进面，宿主文档用这些扩展名时全绿不覆盖它们（本轮只把边界写进规范，不扩面）。个案二：显式路径面内没有 `.agents/` 子树时结构组整体不跑。个案三：空 `.agents/`（部分载荷落地、文件级搬运后的形态）与完整树同形全绿——判据写的是「面内有没有 `.agents` 目录」，不是「有没有结构可判」。个案四：`docs/` 是类型-家盲区——一份 `Type: plan` 放 `docs/` 零告警，而规范明写 `docs/` 不装计划与提案。个案五：空集不冒充通过被载荷自带的 12 篇垫成非空后失效（无损调研「反例」节；修复笔记「Decision」节）。

**根因五：分发与复制形态自己新增的失败——假成功与不可回退的破坏面。** 个案一：`cp -R`（不带 `-n`）会覆盖宿主未提交、未跟踪的内容，且丢失的字节在全部 git 历史里零命中——「无不可回退副作用」不成立。个案二：`npm pack` 静默丢弃载荷里的 3 个桥符号链接（零 warning），于是「两种形态等价、模板目录自足」的声明在 tarball 形态上为假：从 tarball 直拷得到零桥工作区，而 `cp -an` 退出码 0。个案三：安装器宣传的 `npm create curia` 在本包不发布的前提下本来也不可用；包名在公共源无人占用，一旦被抢注，该命令会在默认配置的机器上静默拉取并执行第三方代码（迁移稳定性调研「实测证据」节；迁移稳定性裁定笔记「Problem」节）。

前史（同一形态的旧事故，说明这不是迁移期才有的问题）：符号链接路径下门禁空转——八份脚本主模块判定失效、一条规则都不查却退出 0，加上归档封印校验被吞掉整段跳过，「改归档笔记再重新封印」可洗白篡改（`.agents/notes/implemented/bug-fix/2026-10-02-gate-silent-bypass-on-symlinked-path.md`）；以及归档工具的缺步事故——归档工具曾缺「重写自身相对链接」一步，48 条链接当场失效；更隐蔽的一类是「目标恰好存在」的静默错链：相对链接解析到另一个真实存在的文件，门禁不报，自证夹具正好踩中这一类、且因为「门禁通过」一直没被发现；而封印是 append-only 的单向棘轮，「搬完再修」没有退路（`.agents/notes/implemented/process/2026-10-10-doc-consolidation-2-0.md`「顺带修好归档机制的一个真缺陷」段；收敛笔记「九处对抗回补」第 ② 条）。

怎么系统地找这类坑（两轮调研实际用的方法，可照抄）：

1. 从两端各写一份定义对撞。一版从规范承诺面推——逐条问「这条承诺今天有没有判据」；一版从失败面推——从已知事故反推事实项。拆出来的必须是可判定事实项：写不出核对动作的不算（两版条目 36 与 34，共 70 条）。
2. 反例优先实测，且优先攻击标了「已达标」的条目——那才是定义敢承诺的部分；六条反例全部实测、全部打在已达标条目上，把两版定义的「已达标」计数当场下调。
3. 在真实形态下实跑，不在想象形态下推演。本轮跑过：空宿主、全占用宿主、部分占用宿主、符号链接父级、空 `.agents/`、脏工作树、重复迁移、tarball 形态、非 main 分支；另有把脚本搬到别的目录执行、在五棵真实宿主仓只读实测迁移后去向。
4. 对每条判据问一句「它测的是性质还是代理」。退出码、`readlink` 字面、单短语搜索、exit-0 全绿、目录存在，都是代理指标；代理本身没有错，错在把「探针通过」当成「性质成立」——共同根因一句话就是这个（无损调研「结论」节）。找到代理后换成性质判据：真解析落点、结构可判、字节核对、内容零丢失。正面例证是：传输面（字节落地、空宿主机制、退出码四态、重跑幂等）经得起反例，因为它核的就是字节本身（同节）。
5. 找到一个洞后，检查同族判据。桥父级与复制步落点是同一个洞；结构组静默跳过与空 `.agents/` 同形只差一步——「留一半等于留一整个洞」，同族要一并堵（修复笔记「Alternatives considered」节）。
6. 不采信自述。对抗审查各自到仓内实测提案声称的数字，逐项给出反例路径；三条候选路线「共同诊断出检查器自身的静默面，却没有一条认领它」——诊断与修复的归属要当场定，否则静默面会落在「那是另一条路线的活」的缝里（迁移稳定性调研「三条候选路线与裁决」节）。
7. 定期回查待决位的触发条件。2.2 删掉风格三组后，2.1 计划里「机械修复」那条 DEFERRED 的触发条件永远不可能成立——这类漂移不是断链、不是措辞过时，机器抓不到，只能靠人回查（`.agents/notes/implemented/simplification/2026-10-19-curia-2-2-check-groups-and-payload-trim.md`「Consequences」节）。

边界也明示：「无损」的可核对性止于接线与身份（载荷在位、桥接上、制品可命名）；内容正确性、规则并入质量、纳管质量、迁移后长期漂移四条今天既无机器判据也无可执行的人工核对清单，属明示的不可判定面（无损调研「结论」「未决与后续」节）。修复批的纪律是只修实测出来的假绿、不造新机制；扩面（如把 `.mdx` 纳入扫描）算新规则，需要独立信号（修复笔记「Alternatives considered」节）。

## 三、为什么检查器只报不改（没有 `--fix`）

问题原文：检查器为什么没有 `--fix`、从不写回文件——这个取舍被论证过吗？先检索再答：在 参考实现仓 `.agents/` 下检索 `fix-doc|--fix|写回|自动修`，成文记录多处命中；按层次列出如下。结论先行：被论证过，而且论证了三次——一次是门禁语义，一次是写入工具的风险史，一次是实测否决。

第一层，门禁与修复器分家（2026-10-02，1.0 时代）：当时确实存在一个独立修复器 `fix-doc.mjs`（对显式路径自动修机械错误，默认 dry-run，`--write` 才落盘；它本身随 2.1 删除面退场）；但「fix-doc 做成门禁的 `--fix` 选项」被明确否决——「门禁语义是「拦下将要提交的内容」，修复器是写入工具；混在一起会让守卫在跑检查时顺手改文件。显式路径 + 默认 dry-run 是更保守的契约。」（`.agents/notes/implemented/process/2026-10-02-gate-toolchain-optimization.md`「Alternatives considered」节）

第二层，写入工具自己的风险史：fix-doc 的保护区机制曾有一个潜伏缺陷——嵌套吞并会把链接目标里的 URL、行内代码包进占位符，`--write` 会把这些内容替换成 NUL 字节落盘，再跑一遍还报「无机械问题」（损坏固化）；审计在临时目录端到端复现，当时的备选「不修，等真实触发再修」被否决，理由是「fix-doc 是写入工具，潜伏的数据损坏路径每多存在一天，风险都在复利」（`.agents/notes/implemented/bug-fix/2026-10-02-workflow-audit-fixes.md`「Problem」「Alternatives considered」节）。另外，它的覆盖面本身是维护面：两类邻接缺口（中英邻接、中文紧邻链接括号）在整理轮次里连续两轮出现，需要补进工具的修复清单（`.agents/notes/implemented/process/2026-10-10-2-0-doc-consolidation-round3.md`；`.agents/notes/implemented/process/2026-10-10-doc-consolidation-round4.md`）。

第三层，2.1 时代的实测否决（2026-10-18）：2.1 计划把「机械修复（`fix-doc` 等价能力）」列为 DEFERRED，原因写着「规范只报不改、控制载荷体量」，触发条件是「出现采用方因存量 6/7/8 噪音放弃报告模式或默认面闸门的实例」。触发回执实测了两棵存量树：3,066 篇 69,625 条与 1,083 篇 18,960 条；机械唯一修法占 94% 至 98%，全手修两树约 23 人日，而真问题在编码预检与链接两组——修复无信息价值；安全机械修等于复刻检查脚本的掩码即第三支脚本，朴素 sed 实测打坏链接与行内代码。结论：不建 `fix-doc`（`.agents/plans/2026-10-17-curia-2-1-implementation.md`「状态记录」2026-10-18 条）。

收口在 2.2（2026-10-19）：风格三组删除后，该 DEFERRED 的触发条件永远不可能成立，条目转「不做」；2.2 的真实价值被写成「翻转默认并删掉开关」——`--skip` 退场，九项不查清单（围栏语言、标题跳级、表格竖线、行尾空白、EOF 换行、段落连排、中英空格、半角标点、emoji）进规范，责任归写作纪律与评审（`.agents/notes/implemented/simplification/2026-10-19-curia-2-2-check-groups-and-payload-trim.md`「Decision」「Consequences」节）。第三方格式化器路线也评估过并裁定不装：能补的只有中英空格一项，段落断行与「一段一物理行」打架，emoji 无合适工具；代价是加依赖与配置，而「不在提交路径里的工具没人会跑」（`.agents/plans/2026-10-19-curia-2-2-implementation.md`「状态记录」2026-10-19 条）。

现行形态（截至 Curia 2.2）：检查器默认只报告、`--strict` 才失败；退出码 0 在非严格模式下有歧义——同时表示「无发现」与「有发现、已列出」，所以「任何读退出码的门禁必须带 `--strict`」；报告模式是给人看的巡检面，不是判据面；检查器只读工作树、从不写回文件；装不装钩子归采用方（`.agents/README.md`「配套脚本规格」节）。

把三层连起来看，取舍的骨架是三句话：其一，写与查是两种语义——混在一起会让守卫顺手改文件，破坏「拦下将要提交的内容」的契约；其二，机械修复的真实成本不在修，在「安全地修」——要复刻检查脚本的全部掩码（正则、保护、幂等），等于维护第三支脚本，而修法唯一性占 94% 至 98% 时，修复也不产生判断信息；其三，只报不改强制人看告警——真问题在编码预检与链接组，需要人的判断，机器只负责把发现摆出来。代价也是明示的：风格面漂移从此不再产生机器信号，「某仓风格干净」无法再用机器结论代证（2.2 决策笔记「Consequences」节）。
