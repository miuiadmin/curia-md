# curia-guide — Curia 设计由来与研究导读

**Version: 0.1.11**
**内容截止：2026-10-20**（对应 Curia 2.2、create-curia 0.3.x）

**仓属：** 2026-10-31 起本导读随 Curia 拆入独立仓；正文出处仍是 参考实现仓内相对路径（历史出处，不随仓移动）。

## 这是什么

`create-curia` 是安装包，它带的是**结论**——规范全文 316 行，读完你会用。

这份 `curia-guide` 带的是**结论背后的东西**：为什么是这样、什么试过不行、新机制该怎么裁决。它零脚本、零依赖、不装进任何 `.agents/` 树、不改变任何采用面——纯文本，读它不需要 Node。

## 给谁读

**给接手 Curia 的人，以及要研究它演进的人。**

**不是给采用方。** 这一条是实测结论，不是谦虚：仓内可核的采用方接触点全指向机械问题（怎么装、桥被占了怎么办、退出码什么意思），移植实测的结论是「共 5 步，无一处需要懂 参考实现仓 历史」。采用方读安装包的 `README.md` 就够了。

## 它回答哪些问题

这九条是一个「要自己造一套类似制度」的人只读安装包时**答不上来**的——本导读的验收面就是它们：

1. 9 类与四组判据的数字是怎么从实测里得出来的？台账里哪些判据拦了多少次、哪些从未触发、什么口径算一次拦截？
2. 检查器曾经有过风格检查组吗？风格三组为什么被删？
3. 被裁掉的六个治理面——断言、Run、受保护交付、注册表、台账、自证矩阵——各是什么、当时长什么样、**各自的触发记录**与退役判词是什么？
4. 载荷为什么没有模板、示例和建档脚本？36 到 21 砍了什么、依据什么？
5. 迁移一棵文档树时，静默失败的清单是什么？怎么系统地找这类坑？
6. 两根布局、3 行头块这些形状是怎么推出来的——考虑过一根或三根吗？为什么不用 YAML frontmatter？
7. 面对新机制提议（要不要加个 X），裁决用的元判据是什么？
8. 机制什么时候该改、什么时候不该改——「还能更好」算不算理由？
9. 检查器为什么只报不改、不做自动修复（没有 `--fix`、从不写回文件）？

## 怎么读

**只想知道「怎么做」**：读 01 与 04。两章里出现的几个机制名（自证矩阵、自证套件、两条硬断言、哈希封印、归档封印族）只在 03 有释义，遇到时翻 03 对应处即可——「哈希封印」「归档封印族」在 03 没有同名小节，按「封印」检索（词条在 03「六个面之后」一节）。这两章的方法层可以直接搬到你自己的项目。

**要自己造一套**：按 01 → 02 → 04 读，03 当负向清单查（什么试过不行）。

**接手 Curia**：按 01 → 03 → 04 读，02 与 05 当参考。

**要把 Curia 迁进既有仓**：以 05 为主读，配 03 的静默失败清单与找法（两章互补，都不是完整清单）。

**别按章次从头读到尾**——03 的历史占比最高（约六成是历史记录），04 的最低（约八成五是可迁移的判据）。

## 每条主张都有出处

正文里每条主张后面跟出处（参考实现仓内的相对路径，写到小节名一级）。**指到的是原件**——本导读是改写与索引，原始记录仍是唯一权威；两者不一致时以原件为准。

出处指向的是参考实现仓 参考实现仓。**你手上如果只有这个包**，出处读不到——那不影响结论的可用性，但意味着你无法自行复核。要复核就得拿到 参考实现仓。

## 体量与口径

五章正文共 **606 物理行**（含空行与表格；口径为 `wc -l`，逐章 129 / 67 / 137 / 144 / 129）。按主载荷逐行归类粗算（容差约 ±10%）：

- **会过时的历史与决策记录**：约 **40%**（第三章最高，约六成）
- **现在仍成立的方法、判据、口径、边界**：约 **60%**（第四章最高，约八成半）

之所以给这个口径：这份导读的价值主张是「怎么做」，而它的原料大半是决策记录。**分章的历史占比差异很大**，按上面的「怎么读」选章比从头读更省。

## 维护契约

- **本导读有自己的版本号（内容快照），与脚手架的 patch 号各记各的。** 脚手架只改自身时不必动导读的号；反之导读改动会改 tarball 字节，故脚手架同批跳 patch。版本对应记在本包开头的「内容截止」行——本导读讲的是哪一版 Curia 机制、对照哪一版脚手架。
- **跳号纪律**：与安装包侧同一条——包内任何文件的改动（任一章、本 README、LICENSE）同批跳 patch 号，使 `curia-guide@<版本>` 唯一对应一份字节；判据是包的字节，不是改动量级，只改本 README 也要跳。
- **内容截止日与 Curia 机制版本写在上面**。机制级变更（如 2.1 → 2.2 这种量级）须同批更新受影响的章；只改安装包内部的发布**不**触碰本包。
- **与脚手架的关系**：本导读住在本仓 `guide/`——**与脚手架（`bin/` + `template/`）同仓**，整仓拷过去即两份都有，不必分别取。`create-curia` 不发布到公共 registry——分发与获取方式见它自己的 [`README.md`](../README.md)。
- **漏同步的后果比不写更坏**：读者信任它。本包没有任何机器信号——没有生成器、没有校验器、不在任何检查器的扫描面内。这是明示取舍。
- **未核实项**：各章末列了「未核实」与「未找到成文推导」的点及核实归属。那些是**故意留白**——查不到就说查不到，不编。

## 边界

- **不替代规范**。规范是 `.agents/README.md`（在安装包里），它是现行形态的唯一权威；本包讲的是由来，不是规则。
- **不是采用材料**。采用方读 `create-curia/README.md`。
- **不承诺普适**。台账的结论来自单个仓 12 至 15 天的窗口，规范明文「其他仓的破坏面分布未知」。本包如实照录这个边界，没有把它吹成通用规律。
- **不含他仓数据**。文中涉及别的仓的实测一律写作「某仓」并保留数字；不出现仓名、本机路径、内网信息。
- **本包是一次显式破例**。01 讲的那条 2.2 载荷裁剪判据（「同一份事实的第二个承载点」——又一份副本、两处可能漂移）同样指向本包；破例成立的理由是「改写与索引而非复制」，由 Owner 显式批准——判据的最小形态本是零新增分发件、一行指针。退出条件：若本包长期无人读、或维护契约两次以上失守，按同一判据砍回一行指针。出处：`.agents/notes/implemented/process/2026-10-20-curia-guide-study-package.md`「Decision」「Alternatives considered」节。
