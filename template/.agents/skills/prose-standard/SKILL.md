# 写作标准（prose-standard）

**总纲：写够以保住合约，然后删掉推理记录、重复与装饰。** 合约 = 读者与维护者依赖的义务、不变量、前置/后置条件、兼容承诺；写多写少的判据是「承重命题是否齐全」，不是字数。

硬规则（一段一物理行、中英空格、全角标点、禁 emoji、只写当前状态、相对链接）见 [.agents/README.md](../../README.md)「写作与格式」节；术语查询见 [GLOSSARY.md](../../GLOSSARY.md)。

## 删改前：逐条核对完整命题

对要删改的段落逐条识别，**每条事实子句存活且更清晰**才算改得好（字数更少本身不是改进）：

- actor 与 action（谁做什么）；
- 条件、时序、顺序；
- 模态：must / may / never；
- 负向保证与例外（「不做什么」「除外」）；
- 归属、副作用、失败模式、后果。

压缩前先问：删掉它，读者会误用或做错简化吗？会——保留；不会——删装饰、留结论，理由链接去它唯一的家。

## 术语自检

`contract / boundary / shape / surface / seam / gate / vocabulary` 不是禁用词——**用前自问「有没有更精确的说法」**，点名具体的 API、字段、检查或失败状态。一概念一词；新术语先进 [GLOSSARY.md](../../GLOSSARY.md) 再使用。

GLOSSARY 的 `_Avoid_` 分两档：带全角 `！` 的是硬禁用词，正文命中由 `check-prose` 直接拦下；不带的是命名指引（别用这个词指这个概念），只能靠审校按语境判断——「流水账」出现在「不写流水账」的规则里、「白名单」是权限模型的真实技术词，机械扫描一律会误报，所以不要给常用词加 `！`。

## Slop 清单（九条自查）

1. **重复规则**：同一条规则出现两处——用特征短语搜一遍，留一个家，其余链接。
2. **超层历史**：把历史或过程写进现状文档——历史进 git、notes、rejected。
3. **状态注解**：正文里写「已完成！」「未来计划……」——状态会腐烂，计划与状态另找归宿。
4. **手工重述**：把目录、清单、模板在另一处再抄一遍——链接权威源。**计数也算**：能由工具报告的数字（类型数、夹具数、门禁项数）不要写进散文，写「由某某脚本报告」，否则每次增删都要追着改。
5. **推理记录**：实现步骤、测试走查、「我是怎么推导出来的」——留结论与理由，删过程。
6. **理由重复**：同一理由在多个相邻条目重复——放到拥有它的唯一一处。
7. **段落墙**：一段承载多条规则和括号旁白——拆段，或把细节降到它的家。
8. **强调通胀**：处处加粗、大写、「关键！」——强调只留给改变行为的子句。
9. **spec-speak**：implemented 笔记里出现「应该」「计划」「验收清单」——implemented 只写现在时现实。

## 三档示例法（校准任何一条写作规则）

每条规则配三档对照：**过度裁剪 / 平衡 / 过度展开**；「平衡」= 该位置所需命题齐全且最省。

例（保留失败模式）：

- 过度裁剪：「返回全局对象。」
- 平衡：「返回已初始化的全局对象；未完成初始化或已被销毁时抛出。」
- 过度展开：逐行描述内部状态机分支与辅助函数调用路径。

## 按位置的覆盖（本仓场景）

必备节由[类型注册表](../../doc-types.json)定，本表只管句子层面「必须写什么、不该有什么」。

| 位置 | 必须写 | 不该有 |
|---|---|---|
| notes 笔记 | 独有 rationale、备选、后果、验证证据、点名缺口 | 迁移计划、验收清单、should 式语言 |
| `survey` / `reference` | 可回溯出处（路径、URL、SHA）、方法与样本范围、失效条件 | 决策因果（去 notes）、无出处的二手结论 |
| `postmortem` | 时间线、证据、完整因果链、影响、预防、行动项归属 | 与因果无关的实现细节、反复劝说 |
| `evidence` | 采集时间、采集命令、环境；原样的事实本体 | 分析与结论（去 survey）、修饰性形容 |
| `plan` / `proposal` / `spec` | 可验证的成功判据；未完成事项含 `DEFERRED: 原因 / 归属 / 触发条件` | 进度叙事、已完成事项的走查 |
| `runbook` | 前置条件、每步的可观察验证、失败恢复 | 原理阐述（链接归属文档） |
| skills 技能 | 行为护栏、范围限制（「是准则不是脚本」）、权威链接 | 产品与运行时契约 |
| 根/子树 AGENTS.md | 每条 1-3 行规则 + rationale 链接 | 故事、示例、可链接处的复述 |
| 代码注释（有代码后） | 非显然的合约与理由 | 代码重述、控制流旁白 |

**文体豁免**：注册表里 `narrative: true` 的类型（`postmortem`、`frozen`）允许叙事文体与时间顺序展开；其余类型一律禁推理记录与过程叙事。豁免只放宽文体，不放宽「每条结论要有出处」。

## 版式（`check-layout` 机械校验）

版式规则清单与豁免细则的唯一权威是 [check-layout.mjs 的脚本头注释](../../../scripts/check-layout.mjs)——写时不必背，被拦下时按报错改，机械类可先跑 `node scripts/fix-doc.mjs --write <路径>`。三条要知道的取舍：裸 URL 与弯引号刻意不收（`Source:` 字段本该露出链接、逐字引英文原话 `“…”` 正确）；表格单元格里写竖线要转义成 `\|` 或包进行内代码。

## 工作流

先读目标文件与相关规范（所属目录 README、[类型投影](../../doc-types.md)、GLOSSARY）→ 按覆盖表判「必须写 / 不该有」→ 逐条核对完整命题、删 slop、三档法校准 → 跑 `node scripts/run-checks.mjs`（版式结构机器判、语义你判，机械错误可先 `fix-doc --write`）。门禁报时效或余量警告时当场处置，不攒着；被取代的决策按笔记铁律新开一篇互链。
